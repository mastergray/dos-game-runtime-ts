## 1. A deployment definition

Specified in [deployment-manifest-spec.md](./deployment-manifest-spec.md)
(2026-10-01); the notes below are the testing record it was drawn from.

Each game page today is a hand copy of the first page with a
`dosbox.conf` beside it, a packed bundle named after it, and a comment
in `main.ts`. Eighteen games (commercial titles kept locally, not in
this repository) showed that what varies per game is a small, nameable
set. Make it one declaration per game and generate the bundle, the
page and the server mapping from it:

| Kind of game | What loading needs |
|---|---|
| A keyboard RPG with copy protection | run its launcher, not the main executable, so the passcode prompt accepts Enter |
| A mouse-driven strategy game | three keyboard prompts every boot (graphics, sound, input) that the game never stores; menus open while the mouse button is held, or with Alt plus the menu letter, so touch needs a hold-to-open mouse or an Alt key; saving is disabled during the first turn; saves ask for a drive then a slot |
| Two simulations | a command line with switches, taken from the game's own batch file |
| An RPG with a sound driver | load the driver before the game; a first-run Sound Blaster yes/no |
| A text-mode board game | a colour-computer question, then function keys for everything; prompts accept upper-case Y/N only (a keypad's letter keys must send Shift); saving writes a file and exits to the DOS prompt, so the autosave must run after the game has quit; continuing with no save file crashes to DOS |
| An RPG | resumes its own aborted game automatically |
| A city simulation | must live in a first-level directory, so the bundle carries a subfolder and the autoexec `cd`s into it |
| A puzzle game | run its VGA launcher directly (the batch autodetects the video card); a machine-type prompt every boot; title menu is F1 to F4, so a phone needs function keys |
| A two-player artillery game | plain executable; a shareware nag (any key) and a slow drawn splash on every boot; two players at one keyboard, so a phone needs the digit and bracket keys |
| A business simulation | plain executable, but the sound config that ships in the folder is silent under DOSBox; the bundle must carry the file its setup program writes for Sound Blaster, so the definition needs a way to overlay files onto the game folder at pack time; saves are files next to the game |
| A platformer | a switch forces Sound Blaster instead of autodetect; the title menu is letters and F-keys, play is arrows plus two action keys; the game polls the keyboard, so a synthetic tap shorter than a frame was missed while a 250 ms hold worked, which matters for touch buttons that pulse a key |
| A planet simulation | switches select the 640×480 16-colour layout with Sound Blaster over the installer's 320×200 choice; a definition could expose the display mode; saves go through its File menu |
| A shooter with a launcher | the launcher asks the sound mode on every boot and then shows an options menu driven by arrows and Space; Space is also fire in play, so touch A maps to Space, the first page whose button map differs from the template |
| A mouse-driven turn-based strategy game | plain executable; boots with its File menu already open and the pointer on it; menus also take arrows, Enter and underlined letters; saves are named files written through File → Save, which the overlay carries |
| A 1985 CGA shooter | `machine=cga` for the right palette and `cycles=fixed 600` because it has no speed throttle, the first page whose DOSBox settings differ from the template; a notice screen on every boot (any key); Space fires and X bombs; high scores and key assignments live in `.DAT` files beside the executable |
| Two plain games | plain executable |

The definition should carry:

- **Load:** game files directory, autoexec lines (drivers, command and
  arguments), the DOSBox settings that matter (machine, cycles).
- **Saves:** the storage key; a one-line hint about how the game saves
  when it only writes on its own command. Some games ship their
  progress file inside the bundle (one game's progress file, which its
  own batch resets from a pristine copy), so "Clear saves" returns to
  whatever state was packed, not to a fresh file; the definition should
  say which files to pack clean.
- **Input:** whether the mouse starts enabled (intro click buffering),
  touch mode on the picture, keyboard filter.
- **Controls per device/orientation:** which touch controls exist,
  their size and placement, and what each maps to; a keypad spec for
  games that need digits, letters or function keys on a phone.
- **Page chrome:** title text, keycap placement (anchor to the
  letterbox area, not the viewport corner, via `DosDisplay.onLayout`).

Decide then whether pages stay self-contained copies or share a shell
generated from the definition. Eighteen copies already drift (one
page's keycap experiment); forty will not be maintainable by hand.

## 2. Touch controls

Done in the manifest shell (2026-10-02): controls are components
(`dpad`, `key`, `modifiers`, `digits`, `fkeys`, `letters`) placed per
orientation by the manifest, in a grid that never covers the picture;
Shift, Ctrl and Alt latch. Hand pages keep the old overlay. Still open:

- Size and placement tuning on a real phone; portrait stacks can run
  below the fold and scroll.
- D-pad feel: radial (current) versus four distinct zones.
- A hold-to-open mouse mode for games whose menus open on button-down
  (the strategy game), or an Alt key as the workaround it has now.
- Trackpad: only for pages that want it; the absolute-touch cursor on
  the picture covers most mouse games on a phone.
